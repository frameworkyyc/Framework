# Websites (Client Portal Website section)

Status: **Phase 2** (client dashboard) on top of Phase 1 (database foundation and Framework Admin). The client Website section exists only where `PORTAL_WEBSITE` is exactly "1"; the flag is unset in every environment until it is approved, so clients still see the "Coming soon" line.

## Model (migration 0011, proposed until approved)
* `websites`: several per client. `status` is `existing | in_development | live`; **"No website" is not stored** (a client with no rows has none). `managed_by_framework` is a separate yes/no, so a client's own live site and a live site Framework manages are different rows of the same status. `origin` says who built it (a site in development is always built by Framework). Domain and hosting are plain facts (provider, who owns it, renewal date) and notes: never credentials. One optional private screenshot (png, jpg or webp, up to 5 MB) in the files bucket under `org/<id>/websites/`; `published` says whether the client may see the website once the section is switched on. Archived websites are hidden, never deleted; up to 12 active per client.
* `website_milestones`: title, status (`todo | in_progress | done`), due date, order; tied to their website and organization by a composite key. Used from Phase 3.
* `support_requests.website_id`: nullable; lets a website change request name its website (Phase 4). The Worker only accepts a website of the same organization.
* The four website services (Design, Redesign, SEO, Maintenance) are rows of `service_prices`, defaulting to a custom quote, and appear in Admin -> Settings -> Service Pricing.

## Admin (this phase)
`/admin/clients/:id/website`: add, edit, archive and restore websites, set or remove the screenshot. API: `worker/portal/admin-websites.js`; data layer `repo/websites.js`; screenshot `website-files.js`.

## Client dashboard (Phase 2, behind `PORTAL_WEBSITE`)
Routes (all `website.view`, owners and members, behind the tenant guard): `/portal/o/<slug>/website` (empty state, one website in full, or a list), `/website/<id>` (one website) and `/website/<id>/screenshot` (the image through an authorised route; same sandboxed headers as every file). Four states: no website (empty state with a "Talk to us" email link; nothing stored), existing, in development, live. Status and "managed by Framework" are shown separately. Data layer `repo/client-websites.js`: only `published = 1` and unarchived websites of the member's own organization, never management notes, `updated_by` or storage details; a missing table reads as no websites but any other database failure is an error, never "no website". Page `website-live.js`. The flag is independent of `PORTAL_SERVICES` and `PORTAL_BRANDING`.

### Live preview (Phase 2b)
The client page shows a website's live homepage in a desktop-style frame **only when that website's own headers permit framing**. `website-preview.js` makes one plain GET per website (https and a public DNS name only, redirects followed by hand, 3 s timeout, cached about an hour per portal origin and address, body cancelled and never read) and applies X-Frame-Options and CSP `frame-ancestors`. Nothing is proxied or rewritten: the visitor's browser loads the website itself. The response CSP gets `frame-src` for exactly the origins that check passed through, on the Website page only (`securityHeaders({ frameSrc })` accepts only plain https origins); every other page and the shared policy are unchanged. The iframe is lazy, has no referrer and no permissions, and its sandbox is `allow-scripts allow-popups allow-popups-to-escape-sandbox` WITHOUT `allow-same-origin`, so the page inside has an opaque origin and cannot read the portal, its cookies or storage (some sites that need local storage may show less). Fallbacks in order: the optional uploaded screenshot in the same frame, then a plain card. A Visit website button is always shown. Only a live or existing website with an https address is checked; the several-website list and in-development sites contact nothing. Which sites are tried is not limited to Framework-managed ones: any website that permits framing is previewed.

### Website management and Additional Services (Phase 3, migration 0012 applied to Staging only)
Beneath the website overview the client page has two quiet sections. **Website management** (per website): *Download website files* (one ZIP Admin uploads and publishes; a disabled "Not available yet" button until then), *Request a change* and *Get support*. The last two are ordinary support requests (`website_change` / `technical_issue`) linked to the website through `support_requests.website_id`, so they reuse the existing thread, statuses, attachments, notifications and Admin handling, under `/website/requests/...`, with the existing `support.view` / `support.submit` permissions, and work without `PORTAL_SERVICES`. **Additional services**: a plain grid from the editable catalogue (`portal_services`, Admin -> Settings -> Additional Services: name, short description, shown or hidden, order) with a Request Service button (owners only) that creates a `service_requests` row keyed `svc-<key>` (one open request per service; the price shown, if any, is recorded with it). A price shows only when Admin has set one in Service Pricing (Starting at or Custom quote; "Included" is not offered for these, so nothing implies a service is already part of the client's plan). Admin handles those requests in the existing request lists, named "Additional service: ...".
Website packages: `repo/website-packages.js`, one current ZIP per website (`website_packages`), starts unpublished after every upload, never extracted or run. Website source files (html, js, php ...) are allowed for this profile only (`files/zip.js` `webSource`); real executables, installers, macro documents and nested archives are still refused, and the general ZIP rule is unchanged. Ceiling 25 MB (the file is held in memory while checked). A client reaches it only through `/website/<id>/files/download`: own organization, website published and not archived, package published; each download is recorded.
Migration 0012 is applied to the Staging database (approved, verified); Production has neither 0011 nor 0012. Without migration 0012 the page still works: the download shows as not available and the services grid shows the built-in defaults; Admin saves are refused as unavailable.

## Phases
1. Foundation and Admin website management (done).
2. Client dashboard behind `PORTAL_WEBSITE` (four states: no website, existing, in development, live) (done; flag off everywhere).
3. Milestones and progress (Admin editor, client timeline).
4. Change requests and feedback on the existing Client Services request infrastructure, independent of `PORTAL_SERVICES`; the service offers for design, redesign, SEO and maintenance.

## Analytics (migration 0028, applied to Staging)
Each website has an Analytics page (Cloudflare Web Analytics traffic and Google Search Console search performance, read through their APIs and cached). See `WEBSITE-ANALYTICS.md` for the design, the credentials and the owner checklist.

## Website dashboard (migration 0030 for updates and tasks, applied to Staging 2026-11-22; Production: not applied)
The Website page is a modular card dashboard on a grey ground (renderers in `website-workspace.js`, styles in `assets/css/portal-website-workspace.css`; the page opts out of the centred container with the same `bleed` option as the Brand Book, and the portal header above it is unchanged). Framework's own language: near monochrome, sharp corners, no shadows, white, black and grey cards of different sizes, the one functional colour (`--signal`) only on an overdue task, status as a small square plus words. Every disclosure is a native `<details>` and **nothing is open by default**; there is no script and no change to the strict portal CSP. Motion is short (about 0.2 s) and switched off under `prefers-reduced-motion`. In order:
1. **Live website** (white, larger) and **Preview changes** (black): each shows the picture of that site, a plain status, the address as small secondary text, and a direct link. "Production" and "Staging" are never titles. The live card shows the screenshot Admin uploaded (`/website/<id>/screenshot`, the existing authorised route) or a neutral "No screenshot yet" panel; the preview card shows a neutral "No preview image yet" panel until a picture exists for it. No stock or invented imagery, ever. "Not launched" and "Not set up yet" are neutral states with no link.
2. **Needs your attention**: updates awaiting the client's decision (**Approve**, or **Reject…** which opens a form that requires revision notes) and tasks Framework needs done (Upload files opens the ordinary request form, Respond and Send your review open an answer form, a review task links to the preview). Rows open in place.
3. **Recent updates**: everything decided or finished, newest first (the latest five, the rest under "Earlier updates"), with the client's own notes on a rejection.
4. **Website traffic**: the genuine Cloudflare Web Analytics figures for the default period (visits, the change against the period before, page views, a daily bar chart), from the same analytics service as the Analytics page (cached 30 minutes; the dashboard waits at most 3 seconds, so the page never hangs on Cloudflare). Stale figures say when they were read; "Not connected yet" and "Couldn't load right now" show no numbers and no chart; the link to Analytics shows only where that page exists.
5. **Request a change**: a closed expander holding the form (type, title, text, optional attachments) that posts to the existing `/website/<id>/requests` endpoint, so it creates an ordinary website change request in the same thread, status and Admin queue as before.
Under the cards, two closed groups keep everything that was on the page: **Details** (status, summary, live preview, progress, facts, SEO, files and support) and **Additional services** (the catalogue; it opens by itself after a service enquiry so its confirmation is seen). A "N need you" chip in the header links to the attention card. On a phone the two website cards sit side by side (each a single tap target), then Needs your attention, Request a change, Recent updates and Website traffic.

### Website screenshots (what exists, and what a later step needs)
Today the only picture is the live site's screenshot, uploaded by Admin (migration 0011: one private object per website, up to 5 MB). Nothing captures screenshots automatically, and the preview has no picture or "captured at" date: that is the next step and **needs a decision first** (a place to store a second image and its capture time, an explicit trigger such as Admin's "Refresh preview" or publishing an update for review, and a capture service: Cloudflare Browser Rendering is the leading option; it needs a Worker secret and its usage limits). The safeguards it must keep: capture only the addresses already stored on the website record (https, never client-typed), a service credential for access-protected staging pages, private storage served only through the organization checks, size and rate limits, the last good image kept with its date, and the neutral state as the fallback. The dashboard already shows a picture whenever one is stored and the neutral panel otherwise, so that step changes no layout.

### Data (additive, `migrations/portal/0030_website_workspace.sql`)
`websites.staging_url` (nullable https address), `website_updates` (kind `approval | info`, status `awaiting_review | approved | rejected | info`, the client's decision, time and who, `decision_note` required by a CHECK for a rejection, `published` draft flag, archive) and `website_tasks` (cta `upload | respond | review | none`, status `open | submitted | done | cancelled`, due date, the client's answer, `published`, archive). Both tables are tied to their website AND organization by a composite key. Nothing existing is changed.
**On a database without 0030 (Production, until it is approved there) the new parts are dormant**: the page shows the Live website card, the Preview card as "Not set up yet", the traffic card and the request expander, with no updates or tasks cards; Admin reads say "unavailable" and writes answer 409. Production keeps working exactly as today.

### Who can do what
* **Admin** (`admin-website-workspace.js`, `admin/assets/website-workspace.js`; behind Cloudflare Access, the admin list and `PORTAL_ADMIN_WRITES`): set the Staging address; create updates (needs approval or informational; draft until "Show to the client"); ask for another review after a rejection (the earlier reason stays in `activity_log`); assign tasks, see the client's answers, mark them done or ask again; archive. Admin cannot fake a client's decision or answer.
* **Owners** approve or reject updates (`website.request`). **Anyone in the organization** may answer a task (`support.submit`) and send change requests. A decision is one compare-and-set batched with its audit row, so a double click, a replay or a race decides at most once; a second attempt is "already decided". **Framework master access previews the page but can never decide or answer for the client** (the buttons are hidden and the server refuses).
* A client sees only published, unarchived rows of a published website of their own organization.

### Not built (decisions for review)
Email to Framework when a client rejects or answers (today Admin sees it in the panel); linking an uploaded file to its task (an Upload task opens the ordinary request form and Admin marks it done); a Home "needs you" count (`workspaceAttention` is ready for it); a Production release (migration through the manual workflow first).

## Production: enabling Staging-address editing
Saving a website's Staging address writes `websites.staging_url`, a column added by migration `0030_website_workspace.sql`. While Production does not have 0030 (the Production D1 verify run of 2026-11-22 lists it as the only pending migration, with 0028's tables present), the save fails by design: the UPDATE meets "no such column", `setStagingUrl` answers `unavailable` (HTTP 409) and Admin says "That isn't available on this site yet (a database change is waiting)". Nothing is written. The Production address is a different column (`websites.url`) and keeps saving.

To enable it safely, in this order, each step approved by the owner: (1) read `migrations/portal/0030_website_workspace.sql` (additive: one nullable column with a CHECK, two new tables, no UPDATE or DELETE; no existing row changes); (2) run "Portal Production D1 migration" with ref `Staging`, mode verify-only (the checks must pass: database is `framework-portal`, pending list is exactly `0030_website_workspace.sql`, tables equal what 0001 to 0028 create); (3) record a Time Travel bookmark for `framework-portal`; (4) run it again with mode apply and the database name typed; it applies only the pending file and verifies tables and indexes afterwards; (5) check Admin: Websites, a website, Environments, edit the Staging address. No code change or deploy is needed: the code is already in Production and starts working when the column exists.


## Environment screenshots (Production and Staging)

Each environment of a website has its own picture, uploaded by hand in Admin: **Websites → a website → Overview → Edit** on the Production or Staging card opens that environment's settings (the address, plus upload, replace and remove for the screenshot; PNG, JPG or WebP up to 5 MB, checked against the file's content). A Staging site is often password protected, so nothing is captured automatically.

* **Storage.** Production keeps using the existing `websites.screenshot_*` columns (so every stored Production screenshot is untouched). Staging uses six new nullable columns, `staging_screenshot_*`, from **migration 0031** (approved for Staging only: it lives in `migrations/portal/` and is applied to Staging through the manual "Portal Staging D1 migration" workflow; Production only through its own manual workflow, after its own approval). Both pictures are private objects in the files bucket; no storage key ever reaches Admin's browser or a client.
* **Before 0031 is applied** the Staging picture is "not available": Admin shows a plain notice instead of the upload control, the API answers 409 `unavailable`, and the client Preview card keeps its neutral panel. Nothing else changes.
* **Admin API.** `GET | POST /clients/:org/websites/:id/screenshot/staging` and `POST .../screenshot/staging/remove` mirror the Production routes (`.../screenshot`, `.../screenshot/remove`).
* **Client Portal.** The Live website card shows the Production picture (`/portal/o/:slug/website/:id/screenshot`), the Preview changes card the Staging picture (`.../screenshot/staging`). Both are served only for a published, unarchived website of the member's own organization, with the same sandboxed, no-store headers.

The two website cards (Live website and Preview changes) are one shape: equal columns and height on desktop and iPad, stacked on a phone; a 16:9 picture area, full-bleed (`object-fit: cover`, anchored at the top, no side bars; a very wide or tall image is cropped, never stretched) with a soft inner edge and a neutral ground while it loads; the same header, status, picture and button positions, and equal-size action buttons.

**Needs your attention** is the client's approval workspace: a clean white card with a restrained amber accent (top edge, count pill, status dot), a heading with the pending count, then one compact card per pending item: a short title, its status, the actions on the card itself, and "View details" in a native disclosure. An update that needs approval gets a green **Approve** and a red **Reject**; Reject opens a feedback box in place (at least 3 characters, required) with **Cancel** and **Submit rejection**. A task keeps its own response or upload action. No script: the Reject toggle is a visually hidden checkbox that the Reject and Cancel labels flip. The posts go to the same routes as before, so a decision moves to Recent updates (the history) and into Admin's activity feed and attention list ("sent revision notes on a website update", "approved a website update"); the page then shows the lower count.

**Who sees what.** A signed-in client **owner** (`website.request`) gets live buttons. A **member** sees the items and "An account owner can approve or reject this update." (no buttons). **Framework master access** (staff previewing the client's portal, `a.staff`) previously saw no buttons at all, because `canDecide` is false for staff by design; it now sees the **same Approve and Reject buttons disabled and labelled "Preview only"** when the previewed role is an owner (`previewDecide`), so the preview shows what a real owner sees. The server rule is unchanged and is what protects it: `postWorkspace` answers 403 for any staff session, and a member's post is refused; neither is a UI-only rule.
